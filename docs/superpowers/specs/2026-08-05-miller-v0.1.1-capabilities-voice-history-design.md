# Miller v0.1.1 Capabilities, Voice History, and Interaction Design

**Status:** Approved design; implementation has not started
**Target:** Miller v0.1.1
**Date:** 2026-08-05

## Purpose

Miller v0.1.1 adds four related product improvements without changing the
v0.1.0 menu-bar assistant identity:

1. optional local wake listening with one owner-defined phrase;
2. durable, auditable Live Voice transcripts that Miller sees only when the
   owner explicitly selects them;
3. streaming follow-tail scrolling that yields immediately to manual review;
4. portable custom tools through MCP, plus the account capabilities already
   available through Codex.

The design keeps Miller's native host, SQLite authority, external official
Codex runtime, Pi provider substrate, and source-first distribution model.

## Product Decisions

- Wake listening is disabled by default.
- One custom English wake phrase is active at a time. `Hey Miller` is the
  suggested initial phrase, not a fixed requirement.
- Live Voice transcript text is saved by default. Audio is never saved.
- Saved voice history is never injected into a model turn without an explicit
  owner selection.
- Miller-owned MCP tools are shared across capable providers by default, with
  provider-level enablement overrides.
- Codex account capabilities remain Codex-only; they are not portable
  credentials or tools that Miller can give to another provider.
- Tool policy is configurable at both server and individual-tool levels.
- Settings are divided into focused tabs rather than appended to the existing
  monolithic form.

## Non-Goals

v0.1.1 does not add:

- wake-phrase model training or arbitrary-language wake detection;
- idle audio recording or wake-listening transcription;
- automatic long-term-memory injection from saved transcripts;
- a new Miller-specific executable plugin ABI;
- portability of Codex account connectors to non-Codex providers;
- arbitrary shell plugins, hooks, automations, or unattended approvals;
- avatar integration.

## Capability Architecture

### Sources

Miller owns one capability registry with three source classes:

1. **Codex account capabilities** are account apps, connectors, and other
   capabilities exposed by Codex App Server for the authenticated account.
   Their authentication and execution remain Codex-owned.
2. **Miller MCP capabilities** are local stdio or secure remote MCP servers
   configured by the owner. These are the portable callable tools available
   to every compatible provider.
3. **Provider-native capabilities** are explicit capabilities unique to a
   provider. They are labeled as such and never presented as portable.

Each catalog entry has a stable Miller identifier, source, server or app,
tool name, display metadata, provider availability, connection state, declared
safety annotations, server policy, optional tool override, and effective
policy. Provider refresh must reconcile entries without silently resetting
owner overrides.

### Provider Routing

#### Codex typed conversation

Codex OAuth typed turns move from the Pi-only reasoning request to ordinary
Codex App Server threads and turns. This supplies the same account-side
capability family already observed in Live Voice. Miller remains the durable
conversation authority; App Server thread state is a provider execution detail
and may be reconstructed from bounded Miller context after relaunch.

The adapter consumes typed item lifecycle events for assistant streaming, MCP
tool calls, dynamic tool calls, account app calls, web searches, approvals,
errors, and terminal status. It retains only the bounded projections Miller
needs for presentation and auditing.

#### Codex Live Voice

The existing realtime route remains the low-latency media path. Its bounded
sideband projection is extended to recognize relevant account-tool lifecycle
and approval activity instead of shape-checking and discarding every raw item.
Unrecognized valid activity remains bounded and ignored. Credential, media,
SDP, hidden reasoning, and raw provider payload rules do not change.

#### Pi and non-Codex providers

DeepSeek and other tool-capable providers remain on Pi. Miller enables Pi's
tool loop and extends the bounded gateway protocol so Pi can request a tool
call, suspend generation, receive Miller's result, and continue. Swift owns MCP
execution and policy; the Node helper does not become a second credential,
approval, or MCP authority.

Models that do not support tool calling continue normal conversation and show
an explicit tools-unavailable state.

### Extension Forms

v0.1.1 supports:

- MCP servers as the universal portable tool substrate;
- custom callable tools supplied through MCP;
- Codex account apps and connectors discovered through App Server;
- Codex plugins available to Codex, with supported MCP and skill components
  projected to other providers when those components are portable;
- selectable skill or instruction packages for compatible providers.

Miller must use production-supported App Server inventory and execution
methods. App Server plugin installation APIs documented as under development
must not become a release dependency. If a plugin cannot be consumed through a
stable Codex surface or projected as MCP/skills, Miller labels it Codex-only
and leaves installation to Codex.

### MCP Ownership

Miller uses one Swift-owned MCP client boundary for local and remote servers.
Local stdio servers launch directly from an absolute executable plus argument
array, never through a shell. Remote servers require TLS except for loopback
development fixtures. Secret values are Keychain references and never plaintext
configuration fields.

The broker bounds tool definitions, arguments, results, concurrent calls,
process output, startup time, call time, and shutdown time. A failed server or
call cannot terminate the conversation host or corrupt another server.

## Policy and Approval

Every server has one default:

- **Read-only automatic**;
- **Ask before changes**;
- **Fully trusted**.

Every individual tool may inherit or override its server default. Missing or
unknown safety annotations are treated as potentially state-changing unless
the owner explicitly marks that tool or server fully trusted. Provider and
managed-policy mandatory approvals always take precedence; Miller does not
bypass them.

The settings UI permits manual policy changes for every discovered server and
tool. A refresh may add, remove, or relabel discovered capabilities, but it may
not discard a still-applicable explicit override without telling the owner.

An approval includes capability origin, server, tool, bounded intent summary,
effective policy, and the available decisions. During Live Voice, the pending
tool interaction pauses and the compact surface presents the approval. Voice
may explain that confirmation is needed but cannot approve itself. Closing,
interrupting, or timing out declines or cancels the pending action cleanly.

## Capability Audit Ledger

Every admitted call records:

- associated conversation, typed turn, or voice session;
- source, server or app, and tool identifier;
- start and terminal timestamps;
- effective policy and applicable override;
- whether approval was requested and the owner's decision;
- success, failure, decline, cancellation, or timeout;
- a bounded sanitized summary when the runtime supplies one safely.

The ledger never stores credentials, authorization material, complete email or
document bodies, raw arguments or provider payloads, hidden reasoning, or
unbounded results. It must distinguish complete visibility from opaque
provider-side activity rather than inventing detail that App Server did not
expose.

Audit records follow their associated Miller conversation or voice session and
are deleted with it. Otherwise, v0.1.1 retains them until the owner deletes
them through **Privacy & Data**; it does not add an implicit expiry policy.

## Live Voice Transcript Persistence

### Storage

A SQLite migration adds dedicated live-session and transcript-entry records.
A session records its stable Miller ID, optional associated conversation,
start and end times, activation source, terminal outcome, and transcript-saving
choice. Each entry records session ID, sequence, user or assistant role, text,
completion state, and timestamps.

Completed provider transcript events are committed idempotently. If a session
ends with a nonempty partial entry, Miller saves it as visibly incomplete.
Replayed or duplicate terminal events cannot create duplicate entries.

Miller stores no audio, wake-listening frames, SDP, raw realtime events,
credentials, or hidden reasoning.

### Controls and Retention

Saving defaults on globally. The owner may disable it globally or for the next
session. Voice sessions appear in history with a clear voice label and support
individual deletion, bounded date-range deletion, complete voice-history
deletion, and export through the privacy surface.

Reset and removal include the new tables and any wake-word preference state.
They do not claim secure erasure.

### Explicit Review

The primary review action is **Ask Miller about these conversations**. It
accepts an explicitly selected session or bounded date range, displays the
attached selection, and supplies only that bounded text to the new turn. If
the selection exceeds the context limit, Miller discloses truncation before
submission.

Historical transcript tools are unavailable to the model until the owner has
created that explicit selection scope. Saved transcripts never silently enter
an unrelated typed or voice exchange.

The dedicated voice-entry schema remains separate from paired typed turns.
Live conversations can contain interruption, incomplete speech, and adjacent
same-role entries, so coercing them into one-user/one-assistant rows would lose
or misgroup audit evidence.

## Wake Phrase

### Donor Boundary and Dependencies

Miller reuses the owner-authored Cortana wake-word capture, coordinator,
suspension, handoff, detector, phrase-compilation, and settings behavior from
its canonical source. No VoiceInk-derived source may be copied or consulted.
The reuse audit must identify every donor file and preserve provenance before
implementation begins.

The detector uses pinned Sherpa-ONNX keyword spotting, ONNX Runtime, and the
small Apache-licensed GigaSpeech keyword model already qualified by Cortana.
Miller records versions, hashes, model origin, licenses, notices, binary
inventory, and bundle impact.

### Custom Phrase Flow

Miller compiles one owner-entered English phrase locally with the bundled BPE
tokenizer. A new phrase must be nonempty, fit token and byte bounds, compile to
a usable token sequence, and pass a short local microphone test before it
replaces the last working phrase. Compilation and calibration require no
network access or model retraining.

### Runtime Behavior

Wake listening defaults off. When enabled and ready, a match opens Miller and
starts Live Voice. If authentication, Codex, microphone, or provider readiness
is unavailable, Miller opens once with the exact issue and suppresses repeated
triggering until state changes.

The detector suspends during Live Voice, audio playback, another Miller
microphone owner, microphone device transitions, calibration, and teardown. It
rearms only after the prior audio owner has released the device. Idle frames
remain memory-only and are never logged, transcribed, or persisted.

Settings expose enablement, custom phrase, calibration, microphone, detection
threshold, keyword score, and state. Invalid edits leave the last working
configuration active.

## Follow-Tail Scrolling

The full conversation window and compact overlay share one follow-tail state
model:

- following begins enabled when the viewport is at or near the bottom;
- streaming text or transcript deltas scroll only while following is enabled;
- manual upward scrolling disables following immediately;
- continued streaming cannot pull the owner back down;
- **Jump to latest** appears while following is suspended;
- returning near the bottom manually or through the control reenables it;
- programmatic scrolling does not move keyboard focus or disturb selection;
- Reduced Motion uses nonanimated movement.

The follow decision is deterministic and testable outside SwiftUI geometry.
Views supply bottom-proximity and user-scroll events to that state model.

## Settings Information Architecture

The existing single long settings form becomes a tabbed window:

1. **General** — activation shortcut, readiness summary, menu-bar and launch
   behavior.
2. **Providers** — Codex authentication and model, external Codex runtime,
   OpenAI-compatible profiles, readiness, and removal.
3. **Voice** — Live Voice readiness, wake phrase, calibration, microphone,
   sensitivity, and transcript-saving default.
4. **Tools & Integrations** — Codex account apps, MCP servers, plugins,
   portable skills, provider enablement, server defaults, per-tool overrides,
   and connection tests.
5. **Privacy & Data** — conversation and transcript retention, audit retention,
   export, deletion, and reset.
6. **Diagnostics** — component versions, sanitized failures, Keychain probe,
   and storage or cache use.

Each tab is focused and independently scrollable where necessary. No tab may
recreate the current multi-screen monolith. Tab selection, keyboard navigation,
VoiceOver labeling, and state preservation are acceptance criteria.

## Failure and Recovery Rules

- Provider capability refresh failures retain the last known catalog but mark
  it stale; they never silently enable a new tool.
- MCP startup and authentication failures remain isolated to that server.
- Tool timeouts cancel the call and publish one terminal audit outcome.
- A tool result arriving after cancellation or generation replacement is
  discarded.
- App Server or Pi loss fails the active provider turn without corrupting the
  durable Miller conversation.
- Wake detector failure disables listening, releases audio, and leaves manual
  activation available.
- Transcript persistence failure remains visible and cannot be represented as
  successfully audited.
- Settings changes that require restart disclose that boundary before saving.

## Verification

### Automated

- SQLite migration, transcript ordering, partial entries, idempotency,
  deletion, export, crash recovery, and write-failure behavior.
- Follow-tail behavior under token streaming, user scrolling, selection,
  Reduced Motion, and conversation switching.
- Wake phrase compilation, bounds, invalid input, calibration, suspension,
  device handoff, rearming, process cleanup, and disabled-by-default behavior.
- Catalog reconciliation, provider availability, server-policy inheritance,
  tool overrides, mandatory-policy precedence, approval lifecycle, cancellation,
  timeout, stale events, and audit redaction.
- A deterministic local MCP fixture invoked through both Codex and Pi adapters.
- Codex account-tool event projection without raw sensitive retention.
- Unsupported-tool provider behavior.
- Clean package, dependency inventory, license and provenance closure, process
  cleanup, cache cleanup, and bounded persistent growth.

### Owner-Visible

- Calibrate and trigger a phrase other than `Hey Miller`.
- Check false-trigger behavior, audio ownership, device changes, teardown, and
  rearming.
- Save, review, truncate visibly, export, and delete voice transcripts.
- Use one safe Codex account connector from typed chat and Live Voice.
- Use the same read-only Miller MCP tool through Codex and DeepSeek.
- Exercise a state-changing MCP tool under every policy level and one
  per-tool override.
- Verify follow-tail and manual scroll suspension in the full window and
  overlay.
- Measure bundle size, idle wake-listening CPU and memory, runtime process
  attribution, and storage growth.

Synthetic success does not close the wake, microphone, account-connector,
approval, scrolling, or provider-interoperability human gates.

## Release Boundary

v0.1.1 may ship only when:

- all deterministic verification passes from a clean source checkout;
- donor and third-party provenance is complete and contains no VoiceInk source;
- capability and transcript privacy documentation matches actual behavior;
- the provider and tool availability UI never overstates portability;
- wake listening remains optional and disabled by default;
- audit, cancellation, reset, removal, and storage-growth checks pass; and
- the owner-visible qualification matrix is complete.

Implementation planning must decompose these features into independently
verifiable packets while preserving this shared architecture and avoiding a
second tool registry or persistence authority.
