# Miller v0.1.1 Task 18.5 UI Remediation Design

Status: APPROVED FOR PACKET AUTHORING
Date: 2026-08-08

## Problem

The first Task 19 owner-visible run proved that Live Voice, transcript follow-tail,
and the external Codex capability route work in the packaged v0.1.1 candidate. It
also exposed two bounded presentation defects:

1. Eight terminal capability rows can consume most of the transcript area even
   though the activity is secondary to the conversation.
2. The macOS `TabView` settings shell can move its category navigation into an
   unintuitive toolbar overflow menu instead of keeping the categories visible.

These are release-candidate presentation defects. They do not justify changes to
capability execution, audit persistence, transcript persistence, provider routing,
or settings contents.

## Approved behavior

### Capability activity

- Keep the eight already-bounded recent terminal activity rows available for
  audit inspection.
- Present a persistent `Capability activity` header with the recent-action count
  and an accessible expanded/collapsed disclosure state.
- When expanded, show the rows in an independently scrollable region whose height
  cannot exceed three two-line rows.
- Expand when a new terminal activity row arrives. Automatically collapse 15
  seconds after the most recent new row. A newer row cancels and restarts that
  countdown.
- Collapsing hides no audit data permanently. Expanding the panel exposes every
  retained row. Do not delete rows, change their retention bound, or change their
  sanitized text.
- Keep capability rows outside the selectable transcript surfaces. Do not add
  clipboard behavior to activity data.
- Preserve the existing transcript `FollowTailScrollView` on the full conversation
  and overlay. The bounded activity panel must no longer crowd out the transcript.

### Settings navigation

- Replace the settings-shell `TabView` with a fixed leading sidebar and one content
  region.
- Use the existing `SettingsSection.allCases` order, titles, symbols, accessible
  labels, selection persistence, and Control-Tab/Control-Shift-Tab behavior.
- Keep all six categories visible at the minimum supported settings-window size.
  The sidebar must not become a toolbar item, overflow menu, double-arrow menu, or
  collapsible split-view column.
- Preserve every settings tab's existing independently scrollable content. Do not
  redesign, merge, rename, reorder, or move any setting.

## Implementation boundary

The activity panel remains a presentation-only projection of the existing
`[CapabilityActivityRow]`. A small deterministic presentation state owns only the
expanded flag and receives `new activity`, `toggle`, and `inactivity elapsed`
events. SwiftUI owns the cancellable 15-second task keyed by the latest row ID.

The settings shell uses a fixed-width sidebar `List` with selection binding rather
than `NavigationSplitView`; the latter may collapse and recreate the defect. The
selected section continues to come from the existing `@AppStorage` key.

No new dependency, database field, provider event, timer service, navigation
coordinator, or reusable design system is warranted.

## Failure and accessibility behavior

- Empty capability activity renders no panel.
- A cancelled auto-collapse task makes no state change.
- Manual expansion and collapse remain available after automatic collapse.
- The disclosure control announces `Show capability activity` or
  `Hide capability activity`, and the header announces the bounded row count.
- Sidebar rows expose the existing section-specific accessibility labels and a
  selected state. Keyboard traversal reaches the sidebar directly without a
  toolbar overflow menu.
- Reduced Motion introduces no animation requirement; neither remediation adds a
  new animation.

## Tests

Deterministic tests cover the activity-state transitions, 15-second task contract,
three-row height cap, independent activity scrolling, transcript follow-tail
retention, fixed sidebar source contract, stable selection and keyboard movement,
accessible labels, and unchanged settings-tab content ownership.

The post-package owner check verifies only the two repaired visual behaviors before
Task 19 resumes. It does not repeat or claim the remainder of Task 19.

## Explicit non-goals

- No capability broker, policy, approval, audit, MCP, connector, or tool changes.
- No transcript model, persistence, selection, Markdown, or follow-tail rewrite.
- No settings-category or settings-content redesign.
- No wakeword, provider, Codex protocol, Gateway, Pi, database, packaging-version,
  signing, notarization, publication, or avatar work.
- No Task 19 approval marker and no Task 20 execution.
